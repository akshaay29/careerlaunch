# Epic 1 Context: Students sign up and build their profile

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Stand up the CareerLaunch foundation and the Student onboarding loop. A Student creates an account, gives explicit consent, uploads Resumes, confirms an extracted Skill Profile, sets Preferences, manages private files, and can delete everything. The epic also delivers the monorepo scaffold, CI guardrails, deploy pipeline and the durable job queue that all later epics depend on. Ingestion (Epic 2), scoring (Epic 3) and tracking (Epic 4) all build on the identity, consent, profile data, events and job infrastructure created here, and those epics must run on free-tier hosting with sleeping servers.

## Stories

- Story 1.1: Project scaffold, CI and deploy pipeline
- Story 1.2: Background jobs that survive a sleeping server
- Story 1.3: Sign up, log in and roles
- Story 1.4: Consent for provider runs and the shared pool
- Story 1.5: Upload and manage Resume versions
- Story 1.6: Skill Profile extracted from my Resume
- Story 1.7: Set my Preferences
- Story 1.8: Store and download my other Documents
- Story 1.9: Delete my account and all my data

## Requirements & Constraints

- **Accounts:** sign up with email and password or Google. Each account has exactly one role, `student` or `admin`, and roles are enforced on the server. Students reach only their own records, and admin routes return 403 to Students. Admins can never read Resumes, Documents or Provider Keys.
- **Consent:** each purpose gets plain-language, versioned, timestamped consent before anything runs. Phase 1 purposes are `provider_runs` and `pool_contribution`. The consent text must cover four things: runs are billed to the Student's own Apify account, LinkedIn's terms restrict scraping, Listings collected under the Student's key are shared with other Students, and the Student's rights under India's DPDP Act. Consent can be revoked, and revoking cancels pending work for that purpose.
- **Resumes:** PDF or DOCX up to 5 MB, with multiple versions and exactly one active. Wrong type or size is rejected with a clear message and nothing is stored. Changing the active Resume must trigger re-scoring later.
- **Skill Profile:** skills, education and experience are extracted from the active Resume. If no text can be extracted, show "We couldn't read text from this Resume. Upload a text-based PDF or add your skills manually." and allow manual entry. Student edits persist across re-uploads until the Student chooses "Reset to extracted".
- **Preferences:** role titles, locations, job types (internship, full-time), batch year, CGPA (10-point), degree, work authorisation, a threshold from 0 to 100 (anything else is rejected), alert frequency and time zone (default Asia/Kolkata).
- **Documents:** PDF, DOCX or plain text up to 5 MB, private to the owner and downloadable only by the owner.
- **Deletion:** the account and all of its data are deleted, including stored files and the Auth user, well within 30 days.
- **Time to value:** onboarding (Resume, Skill Profile, Preferences) takes about 10 minutes of effort or less, and a Provider Key is optional.
- **Non-functional:** free tiers only, so the app must tolerate sleeping instances with no always-on worker. Jobs are idempotent and retry safely. Student isolation is enforced on the server. Data is minimal. The database stays near 0.5 GB and files go to object storage. Every job run is logged. The UI is responsive web, in English only.

## Technical Decisions

- **Monorepo:** `api/` uses FastAPI 0.162.0 on Python 3.14, async SQLAlchemy 2.1.8 + psycopg 3.3.8, Alembic 1.20.1, Procrastinate 3.10.0 and pydantic-settings. `web/` uses Next.js 16.4.5, React 19.3.1, TypeScript 5.9.3 and Node 26 LTS, styled with Tailwind CSS and shadcn/ui. `supabase/` holds CLI config only. Pin the versions in the spine's Stack table exactly.
- **Single data gateway:** only `api` touches Postgres or Storage. `web` calls the API only through the client generated by `@hey-api/openapi-ts` into `web/src/api/`, which is never hand-edited. `web` uses Supabase for Auth only.
- **DB exposure:** every table, Procrastinate's included, lives in schema `app`. RLS is on, and `anon`/`authenticated` have no grants. A CI check fails if any table sits in an exposed schema.
- **Modules:** `core/`, `ports/`, `adapters/` and `modules/{accounts,profile,listings,matching,tracker}`. Each module has `router/service/repo/models/schemas/tasks/events`. Services take the session and never commit; only routers and tasks commit (one unit of work each). The module order is `accounts ← profile ← listings ← matching ← tracker`, and import-linter enforces it. Vendor SDKs may be imported only in `adapters/`.
- **Events:** typed domain events in `core.events` are published inside the caller's transaction, and subscribers run synchronously before commit. This epic publishes `ResumeActivated`, `SkillProfileChanged`, `PreferencesChanged`, `ConsentRevoked(owner_id, purpose)` and `AccountDeleting`.
- **Jobs:**
  - Enqueue only through `core.jobs.enqueue(session, task, key, run_at=None, queue='default', **ids)`, which writes a `job_outbox` row in the same transaction. Calling Procrastinate `defer` from `modules/` is forbidden.
  - Job arguments are ids only. The key format is `<module>.<task>:<entity_type>:<id>[:<scope>]`.
  - Recurring work goes through the `schedules` table and `scheduler_tick`, never `@app.periodic`.
  - The default retry policy is exponential backoff, up to 5 attempts.
  - After a Student-initiated profile change, the router starts a bounded in-process drain of the `priority` queue after the response.
- **Drain:**
  - `POST /internal/jobs/drain` is protected by a secret compared in constant time, accepting two values during rotation. It returns 202.
  - Each drain flushes the outbox, runs `scheduler_tick`, re-queues stalled jobs, then runs the worker (`priority` queue first) under a cap of 4 minutes or less, and records `last_drain_at`.
  - `pg_cron` + `pg_net` call the drain every 5 minutes (timeout 90 s or more), with the secret read from Supabase Vault.
  - A GitHub Actions workflow calls `GET /internal/health` every 15 minutes. Health returns 503 when the last drain is more than 15 minutes old, which fails the workflow, and the workflow then runs a backup drain.
- **Identity:** `accounts.id` equals the Supabase Auth uid. Every request has its JWT verified (signature, `aud`, `exp`), and the role is loaded from the DB, never from client claims. Admins are created only by the `promote-admin <email>` CLI, which writes to `admin_audit`. Every Student-owned table has a non-null `owner_id` with `ON DELETE CASCADE` from `accounts`.
- **Consent gate:** `accounts.service.require_consent(owner_id, purpose)` is the only check. Callers run it at enqueue and again inside the job. Without consent it raises a typed error that maps to a 403 problem+json with type `consent-required`.
- **Files:**
  - `profile.service` checks magic bytes and the 5 MB limit, then stores through the `FileStore` port at `<owner_id>/<kind>/<uuid>` in a private bucket.
  - Downloads use signed URLs that expire in 5 minutes or less, with `Content-Disposition: attachment`. Another Student's id returns 404.
  - Extraction (pdfplumber 0.11.10 / python-docx 1.2.0) runs as a `priority` job in a subprocess with memory and time limits, and a crash must not affect API health.
- **Skills:** `core.skills` holds a versioned canonical vocabulary with aliases, and `normalize(text) -> set[skill_id]` returns stable kebab-case slugs. Stored skill sets record `vocab_version`. Student edits are stored as `added` and `removed` sets applied over the extracted set. No module keeps its own alias table, and custom skills are stored but not scored.
- **Data:**
  - The DB enforces constraints: a partial unique index allows one active Resume per Student, there is one `preferences` row per Student, and a check constraint keeps the threshold within 0–100.
  - IDs are UUID v7 generated in the app, except `accounts.id`. Times are UTC `timestamptz`.
  - All connections go through the Supavisor session pooler (port 5432).
- **Ops log:** `core.ops.record_event()` writes to `ops_events`, which is append-only and holds ids and counts only. `admin_audit` is insert-only. Both set their Student foreign keys to NULL when the Student is deleted.
- **Account deletion:** one transaction publishes `AccountDeleting` and cascades every Student-owned row, then enqueues idempotent jobs: `purge_files`, which removes everything under `<owner_id>/`, and `AuthAdmin.delete_user`.
- **API conventions:**
  - Errors are RFC 9457 problem+json from one handler, with field-level errors for validation. Lists use cursor pagination.
  - Route classes are `/api/v1`, `/api/v1/admin`, `/api/v1/public` and `/internal`.
  - `web` sends the bearer token from its `@supabase/ssr` cookie session. CORS allows only the Vercel origin and localhost.
- **Migrations and CI:**
  - Alembic owns all DDL, including the Procrastinate schema, the `pg_cron` schedule, RLS and grants. Never edit the schema in the dashboard.
  - Prod migrations run from GitHub Actions through the session pooler before the Render deploy hook fires, and are expand-then-contract.
  - CI runs pytest against local Postgres with port fakes, import-linter, the exposed-schema check and the OpenAPI client diff.
- **Config and logging:** one pydantic-settings class. `.env.example` lists every key and where it lives. Logs are structured JSON with no secrets.

## UX & Interaction Patterns

- There is no UX design document. Screens are defined by the behaviour and states in each story.
- After sign-up, the Student lands on onboarding: consent, Resume, Skill Profile, then Preferences. The consent screen is also reachable from settings.
- Upload and validation errors use clear, human messages. Extraction failure shows the fixed message above and offers manual skill entry.
- Account deletion requires the Student to type their email to confirm.
- Untrusted text is rendered as plain text, never HTML. The tone is neutral and factual.

## Cross-Story Dependencies

- 1.1 comes before everything else. 1.2 (jobs, `ops_events`) is needed by 1.6 (extraction job) and 1.9 (purge jobs). 1.3 (accounts, auth, `admin_audit`) is needed by every Student-facing story.
- 1.5 publishes `ResumeActivated`, which 1.6 consumes. 1.5 and 1.8 share the `FileStore` upload and download path.
- 1.9 relies on every earlier table declaring `owner_id` with `ON DELETE CASCADE`.
- Later epics use this epic's work:
  - Epic 2 uses `require_consent`, `ConsentRevoked`, `PreferencesChanged`, `schedules` and `core.skills`.
  - Epic 3 subscribes to `ResumeActivated`, `SkillProfileChanged` and `PreferencesChanged` through `mark_stale`.
  - Epic 4 links Applications to Resume versions.
